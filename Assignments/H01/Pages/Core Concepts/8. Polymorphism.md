# Polymorphism in C++
The ability of a single interface, like a function name or an operator, to represent different behaviors depending on the context or data types involved.

It is categorized into two main types: **Compile-time** (Static) and **Runtime** (Dynamic).

## Compile-Time vs Runtime
### Compile-Time Polymorphism (Static)
Also known as early binding or static binding, this occurs when the compiler selects the appropriate function or operator at compilation time.
- Function Overloading: Multiple functions with the same name but different parameters (number or type).
- Operator Overloading: Giving standard C++ operators (like + or <<) special meanings for user-defined types.
- Templates (Parametric Polymorphism): Using templates to write generic code that can work with any data type, resolved at compile time.

Also known as late binding or dynamic binding, this occurs when the specific function implementation is determined during program execution.

### Comparison Table

| -- | -- | -- |
| **Binding Time** | During compilation | During execution |
| **Execution Speed** | Faster (no runtime overhead) | slightly slower (due to vtable lookup) |
| **Flexibility** | Less flexible; fixed at compile time | Highly flexible; adaptable at runtime |
| **Mechanism** | Function/Operator Overloading, Templates | Virtual Functions, Pointers/References |

## Why It Matters
Polymorphism is a core pillar of Object-Oriented Programming (OOP) in C++ that allows a single interface to represent different underlying forms. It is essential for building scalable, maintainable, and flexible software. 

1. Code Extensibility and the Open-Closed Principle 
   - Polymorphism allows you to write code that can be extended without being modified. For example, if you have a Shape base class with a draw() method, you can add new shapes like Rhombus later without changing the existing logic that iterates through and draws all shapes. This aligns with the Open-Closed Principle (open for extension, closed for modification). 

2. Unified Interface for Diverse Types 
   - It enables the creation of generic algorithms and containers that operate on objects of different types through a common interface. 

3. Runtime Flexibility (Late Binding)
   - With Runtime Polymorphism (achieved via virtual functions), the decision of which function to execute is made at runtime based on the actual object type. This is critical for: **Plugin Systems** and **Dynamic Behavior**

4. Code Reusability and Abstraction
   - **Reduces Boilerplate:** You can define common behaviors once in a base class and override only what is unique in derived classes, preventing code duplication.
   - **Decoupling:** Polymorphism separates the "what to do" (interface) from the "how to do it" (implementation). This makes the system more modular and easier for teams to work on separate components. 


5. Efficient Compile-Time Dispatch
   - C++ also supports Compile-Time Polymorphism through function overloading and templates. This allows for: **Type-Safe Generics** and **Performance**

## Common Mistakes with using Polymorphism
1. **Missing Virtual Destructors:** If a base class has virtual functions but lacks a virtual destructor, deleting a derived object through a base class pointer results in undefined behavior. Typically, only the base portion is destroyed, leading to memory leaks in the derived object.
2. **Object Slicing:** This occurs when a derived class object is assigned to a base class object (by value) rather than using a pointer or reference. The derived-specific data is "sliced off," and the object loses its polymorphic behavior.
3. **Mismatched Function Signatures** If a derived class function has a slightly different signature (e.g., missing const or different parameters) than the base class virtual function, it hides rather than overrides the base function. Use the `override` keyword to let the compiler catch these errors.
4. **Calling Virtual Functions in Constructors/Destructors:** During construction or destruction, an object's type is considered to be that of the class currently being executed. Virtual calls will not reach derived overrides because the derived part does not yet exist or has already been destroyed.
5. **Inheritance for Code Reuse:** Using inheritance merely to share code (instead of representing an "is-a" relationship) leads to rigid and highly coupled designs. Composition is often a better alternative.
6. **Ignoring Static Polymorphism:** Many developers rely solely on runtime (inheritance-based) polymorphism. For many use cases, templates (static polymorphism) provide a faster, zero-overhead alternative.
7. **Neglecting Performance Costs:** Runtime polymorphism involves an extra indirection via a vtable (virtual table). In performance-critical loops, this can hinder compiler optimizations like inlining.
